# やること抜けチェッカー 仕様書 V0.3

## 1. 作品の位置づけ

- 大分類：AI Business Workflow Automation
- 作品名：Action Item Checker
- 日本語名：やること抜けチェッカー(旧称：AI Handover Guard / AI引き継ぎ漏れ防止ツール)
- 目的：申し送り文章から次の行動を抽出し、担当・期限・作業内容などの不足を警告する

## 2. 誰でも理解できる一文仕様

> 職場の申し送りを「誰が・何を・いつまでに」へ整理し、決まっていない項目を知らせるツール。

## 3. 利用者

| 利用者 | 必要な情報 |
|---|---|
| 一般職員 | 自分が担当する作業、期限、注意点 |
| 管理者 | 担当者不明、期限不明、期限超過、重要案件 |
| 改善担当者 | 漏れや曖昧さが多い連絡の傾向 |

## 4. V0.3の対象範囲

### 実装するもの

- AIへ渡す原文と、人間が決めた正解表の分離
- AI抽出後を想定したCSVの読み込み
- 必須項目の不足判定
- 警告理由の作成
- 監査結果CSVの出力
- 項目別正解率と全項目正解率の計算
- 単体テスト
- OpenAI APIを使った最大10件の安全な抽出試験
- 担当者名の敬称正規化
- 項目ごとの不一致明細
- 保存済みAI回答の監査・評価一括実行
- AI優先度とPython優先度の独立比較
- 優先度不一致の要確認表示
- 対応内容の完全一致と正規化一致の分離

### まだ実装しないもの

- メール、Slackなどへの自動通知
- GUI
- 実在する職場データの利用
- AIによる自動返信

## 5. 入力項目

| 項目 | 説明 | 必須 |

| submitted_at | 登録日時 | 必須 |
| source_department | 発信部署 | 必須 |
| message_text | 元の申し送り文章 | 必須 |
| extracted_action | AIが抽出した作業 | 条件付き必須 |
| extracted_assignee | AIが抽出した担当者 | 条件付き必須 |
| extracted_deadline | AIが抽出した期限 | 条件付き必須 |
| extracted_priority | AIが判定した緊急度 | 必須 |
| action_required | 対応が必要か | 必須 |

## 6. 監査ルール

対応が必要な申し送りでは、次の3項目を必須とします。

1. 作業内容
2. 担当者
3. 期限

不足がある場合は `NEEDS_REVIEW`、不足がない場合は `READY` とします。対応不要の場合は `INFO_ONLY` とします。

優先度はAI結果を上書きせず、Pythonが原文から独立判定した `rule_priority` と並べます。不一致は `priority_audit_status=NEEDS_REVIEW` として人が確認できるようにします。

## 7. 視点をずらした部分

一般的なAI要約ツールは「文章を短くする」ことが中心です。本作品は、要約の上手さではなく「次の行動が実行可能な状態になっているか」を監査します。

## 8. 高値更新として示す部分

- AIと固定ルールを組み合わせる
- 正解ラベル付きデータで性能を測る
- 利用者別の表示を設計する
- 処理件数ではなく、不足項目の発見率を評価する
- 将来は通知まで含む一連の業務フローにする

## 9. 成功指標（将来版）

| 指標 | 意味 |
|---|---|
| 項目抽出正解率 | 担当・作業・期限を正しく取り出せた割合 |
| 不足検出再現率 | 本当に不足している案件を見逃さなかった割合 |
| 誤警告率 | 問題のない案件を誤って警告した割合 |
| 処理時間 | 人が確認する場合と比べた所要時間 |

## 10. 設計原則

- 処理単位ごとに見出しやコメントを付ける
- AIが不確かなときは、人による確認へ回す
- 業種固有ルールは設定で変更可能にする
- 元文章と判定理由を残し、後から確認可能にする
- 個人情報を含む実データは使用しない

## 11. V0.4追補：期限超過の判定(2026-09-29 追加)

### 背景

設計にあたり、次の考え方を前提とした。「顧客が『1週間以内に対応してください』と示していても、それは上限であって、4日目まで放置してよいという意味ではない」。また、即対応がどこまで求められるかは場面によって違う。仮の例として、社内向けの定例連絡では即対応が必ずしも求められない一方、通信販売の受注窓口で商品の破損・誤配送・品質不良といったクレームが発生した場合は、担当者がすぐ動くのが通例と考えられる。この2点から、「即対応の必要性は業種そのものより、案件の重さ(クレーム性)による」と整理した。

### 判定基準

- 緊急度「高」(既存のPython側緊急度自動判定を使用。クレーム・苦情・事故・安全等のキーワードで判定):文中の期限に関わらず、登録(`submitted_at`)から一定時間(既定4時間)以内に着手されていなければ`sla_audit_status=NEEDS_REVIEW`とする。この時間は`--sla-hours`で変更可能なサンプル値であり、実運用では業種・組織に合わせて調整が必要
- 緊急度「中」「低」:これまでどおり、文中の期限(`extracted_deadline`)を基準に判定する
- 対応不要(`action_required=false`)の案件は判定対象外(`NOT_APPLICABLE`)
- 期限が時刻のない日付のみ(`YYYY-MM-DD`)の場合は、その日の終わりまで有効とみなす(14.3参照)

### 既知の制約

現在のデータには、実際に「いつ着手したか」「いつ対応が完了したか」を示す項目がない。記録されているのは登録日時と文中の期限のみであり、この監査は「CSVに書かれた内容を見る一時点のスナップショット」である。実際の対応状況を継続的に追跡する仕組みには、今のところなっていない。判定の基準日時(`--as-of`)を指定できるのはこのためで、省略時は実行時刻を基準にする。

## 12. V0.4追補：重複候補の判定(2026-09-29 追加)

### 背景

同じ担当者・同じ作業内容の申し送りが短期間に複数回登録されている場合、誤って二重登録してしまったケースや、違う人が同じ案件を別々に報告したケースが考えられる。これらは対応漏れではなく対応の重複・混乱につながるため、V0.4のもう一つの判定として追加した(1つ目の候補案として提示した「同じ担当者・同じ作業内容が短期間に複数回登録されている」という定義を採用)。

### 判定基準

- 対象は`extracted_assignee`(担当者)と`extracted_action`(作業内容)が両方確定している案件のみ
- 作業内容は空白・句読点(全角/半角)の差を無視して比較する(表現のわずかな違いを別案件と誤認しないため)
- 同じ担当者・同じ作業内容の組み合わせが、一定時間(既定24時間、`--duplicate-window-hours`で変更可能なサンプル値)以内に複数回登録されていれば、両方(またはそれ以上)を`duplicate_audit_status=NEEDS_REVIEW`とし、どのIDと重複しているかをメッセージに残す
- 対応不要(`action_required=false`)の案件、担当者・作業内容が未確定の案件は判定対象外(`NOT_APPLICABLE`)
- 登録日時が読み取れない案件は`UNKNOWN`とする

### 既知の制約

- あくまで「目安」であり、重複＝誤りと決めつけるものではない。実際に別々の対応が必要な案件が、たまたま同じ担当者・同じ表現で短期間に登録されることもある
- 判定は今回読み込んだCSVの範囲内でのみ行われる。過去に監査済みのCSVとの突き合わせ(履歴をまたいだ重複検出)は、今のところ対応していない
- 100件の試験データ(`data/mock_ai_output.csv`)には、似た内容の案件が約2日おきに再発するパターンが含まれているが、既定の24時間の目安を超えているため重複候補としては検出されない。これは試験データの傾向によるものであり、実装の不備ではない(実際に短期間の重複を1件追加して、正しく検出されることを確認済み)

## 14. V0.4追補：100件検証で分かった既知の課題(2026-10-02 追加)

100件検証(`docs/VALIDATION_REPORT.md` 8章)で、次の課題が見つかった。14.1・14.2は修正しておらず、既知の課題として記録する(14.3だけは小さな修正で済むため、のちに修正した)。結果を見てから同じ100件に合わせてプロンプトやルールを調整すると、点数は上がっても未知の文章への強さは示せないため、今回は記録を優先した。

### 14.1 曖昧な作業内容を要確認にできない

「例の件を○月○日17時までにお願いします」のように、作業内容が特定できない文が9件ある。正解は「作業内容が不明なので要確認(`NEEDS_REVIEW`)」だが、AIは作業内容に「例の件」「例の件をお願いします」と出力した。6章の監査ルールは作業内容が空欄かどうかだけを見るため、9件すべてが`READY`になった。

- 要確認にすべき49件のうち検出できたのは40件(不足検出再現率 約82%)
- 問題のない51件(`READY` 41件・`INFO_ONLY` 10件)を誤って警告したものは0件(誤警告率0%)

### 14.2 時刻のない期限の扱いが決まっていない

「○月○日までに」と時刻のない文が9件ある。正解表は期限を17:00としているが、これは文中にない前提である。プロンプトも時刻がない場合の扱いを指示しておらず、AIの出力は23:59(5件)・日付のみ(3件)・00:00(1件)にばらついた。

### 14.3 日付のみの期限が期限超過の判定をすり抜ける(2026-10-02 修正済み)

11章の期限超過の判定は、期限を`YYYY-MM-DD HH:MM`の形式でしか読み取れない。14.2で日付のみが出力された3件は「期限が未確定のため判定できません」(`NOT_APPLICABLE`)と表示され、期限が書かれているにもかかわらず判定の対象から外れた。

### 修正内容(2026-10-02)

期限が「YYYY-MM-DD」の日付のみの場合、その日の終わり(翌日0時の直前)まで有効とみなして判定するようにした。たとえば期限が`2026-09-18`なら、9月18日の23:59までは「期限内」、9月19日の0:00以降は「期限超過(要確認)」になる。時刻を勝手に決めない(17:00などを前提にしない)ことで、期限内の案件を誤って警告することが最も少なくなる考え方を採った。メッセージには「文中の期限(日付のみ)」と明記する。「YYYY-MM-DD HH:MM」の期限の判定、読み取れない期限(「来週中」など)が「判定できません」になる動作は変えていない。

100件の実際のAI出力で再実行したところ、日付のみの3件(H011・H021・H031)は、基準日時が2026-09-20 09:00のとき期限超過、2026-09-17 12:00のとき期限内と判定された(修正前はどちらの基準でも「判定できません」)。

ただし、14.2の「時刻のない期限をどう扱うか」(正解表の17:00という前提と、AIの出力のばらつき)は、まだ決めていない。今回の修正は、監査側が日付のみの期限を読めるようにしただけである。


## 15. V0.4追補：Excel版の出力(2026-10-02 追加)

### 背景

監査結果のCSVは項目名が英語で、列幅も調整できない(CSVには列幅を保存できない)。一般職員や管理者が読むには、日本語の見出しと読みやすい列幅が必要なため、人が読む用のExcel版を追加した。

### 設計

- `output/audit_result.csv`は変更しない。評価処理(`evaluate_predictions.py`)とテストが英語の項目名で読むため、機械が読む元データとして残す
- `output/audit_result.xlsx`を`src/excel_report.py`で追加する。`audit_rules.py`と`run_trial_pipeline.py`が実行時に同時に作る
- 1行目に英語の項目名、2行目に日本語見出し。値のうち判定系の列(項目の充足・総合判定・緊急度の照合結果・期限超過の判定・重複の判定・対応要否)は「英語(日本語)」で併記する
- 列幅は内容の表示幅(全角2・半角1)から自動で決める。内容が長い列は2行に折り返して縮め、全行の高さをそろえる。3行以上が必要な行だけ高くする
- 見出し行と識別番号の列を固定し、日本語見出し行に絞り込みを付ける

### 既知の制約

- 見た目の確認は、作者が実際にExcelで開いて行った。他のExcel互換ソフトでは折り返しの位置が少し異なる場合がある
- 判定の日本語表記は、現在の判定名(`READY`など)に対する対応表である。判定名を増やした場合は`excel_report.py`の対応表も更新する

## 16. V0.6追補：APIサーバー(2026-10-02 追加)

### 背景

これまでは、コマンドラインでCSVを処理する使い方に限られていた。他のツールやプログラムから、監査・期限超過の確認・AI抽出を呼び出せるようにするため、FastAPIでAPIサーバーを追加した。

### 設計

- 追加ファイル：`src/api.py`(APIサーバー)、`tests/test_api.py`(APIテスト19件)
- 入口：`GET /health`(動作確認)、`POST /audit`(監査)、`POST /overdue`(期限超過の一覧)、`POST /extract`(AI抽出)
- 判定ルールは`audit_rules.py`の`audit_records()`をそのまま使い、CLI版と判定が分かれないようにした。実際のAI出力100件で、CLI版とAPI版の判定(総合・期限超過・重複・優先度とそのメッセージ)が全件一致することを確認した
- `/audit`は判定結果に加えて、件数のまとめ(問題なし・要確認・共有のみ・期限超過・重複候補・優先度の不一致)を返す。`/overdue`は期限超過(要確認)の記録だけを返す
- `/extract`は有料API通信のため、`confirm_paid_api`がtrueのときだけ実行する。1回のリクエストは10件まで。キーが無い場合は503、AI側の失敗は502で返し、例外の内容(キー等を含み得る)は返さない
- AI抽出の処理は、CLI版(`llm_extractor.py`)の共通関数`extract_records()`に切り出して両方から使う。CLI版の動きは変えていない
- 入力の検証：件数の上限(監査500件・抽出10件)、`as_of`の形式、`sla_hours`などが0以下でないことを、不正なら422で返す

### 既知の制約

- 認証機能がない。自分のパソコン内(127.0.0.1)での利用に限る
- 記録の保存はしない(受け取って判定して返すだけ)。過去分との重複検出は、データベース追加(更新計画3)で扱う
- `/extract`の本物のAPIでの動作は、この追補の時点では未確認(テストは偽のクライアントによる)。有料のため、作者の承認を得て別途確認する

## 17. V0.7追補：履歴の保存と、過去分にまたがる重複検出(2026-10-03 追加)

### 背景

重複候補の判定(12章)は、1回に渡した記録どうしの比較に限られていた。別の日・別の回に登録された同じ内容は見つけられないため、記録をSQLiteに保存し、前回までの分とも比べられるようにした。

### 設計

- 追加ファイル：`src/history_store.py`(保存と、履歴つきの監査)、`tests/test_history_store.py`(19件)。`src/api.py`に`POST /history/audit`と`GET /history`を追加し、`tests/test_api.py`に5件を追加した
- 保存先は`output/history.db`(SQLite。標準ライブラリのみ使用)。`.gitignore`の`output/*.db`で除外する
- 保存するのはAI抽出済みの記録(`record_id`・`submitted_at`・`source_department`・`message_text`・`extracted_action`・`extracted_assignee`・`extracted_deadline`・`extracted_priority`・`action_required`)と保存日時。判定結果は基準日時で変わるため保存せず、毎回計算し直す
- `audit_with_history()`は、今回の記録の登録日時の前後に重複判定の時間枠を足した範囲の履歴を取り出し、履歴と今回の記録をまとめて既存の`audit_records()`で監査して、今回の分だけを返す。判定ルール自体は変えていない
- 同じ`record_id`の記録は`INSERT OR REPLACE`で置き換え、比較の対象からも外す(同じ記録の再送で自分自身と重複扱いにしない)
- 登録日時を読めない記録は履歴との比較をせず、従来どおり「判定できません」にする
- 実際のAI出力100件を時間がバラバラな4回に分けて監査した結果：重複候補は、履歴なし4件、履歴あり9件、まとめて監査13件。最終回の25件は、まとめて監査した場合と全件一致した

### 既知の制約

- 先に保存された記録は、あとから重複が届いても更新されない。重複はあとから届いた側にだけ表示される(先の記録に遡って「重複」とは付かない)
- 同じ`record_id`を別の内容で送ると、前の内容は上書きされる
- 認証・削除・一覧取得の入口はない(自分のパソコン内での利用が前提)
- 履歴が増えたときの速度は未検証(登録日時で絞って取り出す設計だが、索引は付けていない)

## 18. 第三者確認(2026-10-03)の指摘への対応

第三者による確認で、再現条件つきの指摘を受けた。再現を確かめたうえで、1件ずつ対応する。

### 対応済み

- **原文がExcelの数式になる**：`message_text`などに`=1+1`を入れると、Excel出力のセルが数式として保存されていた(保存したxlsxに`<f>1+1</f>`が存在)。文字列は必ず文字のセルとして保存するよう修正した。`=`・`+`・`-`・`@`で始まる文字列と、保存後のXMLに数式要素がないことをテストで確認している
- **同じrecord_idで履歴が1件消える**：同じ回に同じIDを2件送ると、結果は2件返るのに保存は1件になり、後の記録だけが残っていた。空のIDと、同じ回の中の重複IDを、保存の前に入力エラー(422)で断るよう修正した。既存のIDを別の回で送り直す更新は、従来どおり許可している

### 対応済み(評価の分母。20章)

- **欠落した予測IDが正解率の分母から除外される**：正解表と回答の両方にあるIDだけを採点していたため、AIの回答が欠けた件があると、その件が分母から消えて正解率が高く見えた。正解表の全件を採点の対象にし、回答がない件は不正解として数えるよう修正した(20章)

### 対応済み(CSVの数式対策。21章)

- **`audit_result.csv`をExcelで開くと、原文が数式として実行される**：採点の元データとして使うため書き換えず、Excelで開く用のCSV(`audit_result_for_excel.csv`)を別に出力する設計にした(21章)

### 対応済み(総合判定の見直し。19章)

- **期限を過ぎていても総合判定が「問題なし」になる**：項目の充足(`audit_status`)と総合判定(`overall_status`)を分け、期限超過・重複候補・優先度の不一致があれば総合判定を要確認にした
- **読めない日時があっても「問題なし」になる**：登録日時が読めない、または期限が書かれているのに書式が読めない場合を「判定不能」とし、総合判定を要確認にした
- **`action_required`の誤記(例：`tru`)が対応不要として扱われる**：true/falseのどちらにも読めない値は、項目の充足・総合判定とも要確認にした。APIでは422で受け付けない

### 注意

H04・H05の修正の前後では、100件の実API検証の成績やREADME記載の数値を再計算していない。総合判定の見直し(19章)では、100件の項目の充足(`audit_status`)が修正前後で1件も変わらないことを確認し、成績の数字は従来どおり項目の充足で採点している。

## 19. V0.8追補：項目の充足と総合判定の分離(2026-10-04 追加)

### 背景

これまでの`audit_status`(日本語見出し「総合判定」)は、作業内容・担当者・期限が書かれているかだけを見ていた。そのため、期限超過・重複候補・優先度の不一致があっても「問題なし」(READY)と出て、利用者に誤解を与えた。第三者確認(18章)で、読めない日時や`action_required`の誤記も同様に見逃されることが分かった。

### 設計

- `audit_status`は意味を変えず、「項目の充足」と呼ぶ。評価処理(`evaluate_predictions.py`)と、100件の正解ラベル・成績はこの値を使い続ける(評価の数字は変えない)
- `overall_status`(総合判定)と`overall_message`(理由)を追加する。要確認になる条件は、項目の不足・期限超過・重複候補・優先度の不一致・判定不能(日時の書式が読めない、対応要否が読めない)のいずれか。対応不要(`INFO_ONLY`)は、そのまま共有のみ。重複候補は複数件を比べたあとで決まるため、総合判定は`audit_records`の最後に作り直す
- 期限が書かれているのに読めない場合は、`sla_audit_status`を`NOT_APPLICABLE`ではなく`UNKNOWN`にする(以前は「来週中」「2026/09/18」なども判定対象外だった)。期限が空欄の場合は従来どおり`NOT_APPLICABLE`
- 対応要否は`parse_action_required`で、`true`/`1`/`yes`/`y`と`false`/`0`/`no`/`n`(大文字小文字・前後の空白は無視)だけを受け付ける。それ以外(`tru`・空欄など)は、優先度・期限・重複を`UNKNOWN`、`audit_status`を`NEEDS_REVIEW`(不足項目「対応要否」)にする。APIの`action_required`は同じ判定で、読めない値は422
- APIの`summary`に`overall_ready`・`overall_needs_review`を追加(従来の`ready`・`needs_review`・`info_only`は項目の充足の件数)
- Excelの日本語見出しは、`audit_status`が「項目の充足」(値の表示は「そろっている」「不足あり」「共有のみ」)、`overall_status`が「総合判定」(値の表示は「問題なし」「要確認」「共有のみ」)
- CSV・Excelは先頭行の項目名で列を決めるため、どの種類の結果も同じ項目を持つようにした(テストで確認)

### 確認

- 修正前の再現(同じ入力・基準日時):期限超過・重複候補・読めない登録日時・書式違いの期限は「問題なし(READY)」、`action_required="tru"`は「対応不要(INFO_ONLY)」、APIは200で受け付けた。修正後は、いずれも総合判定が要確認になり、APIは422になる
- 実際のAI出力100件(基準日時2026-09-20 09:00):従来の項目は全件同一(差分0)。項目の充足は問題なし50・要確認40・共有のみ10のまま。総合判定は問題なし15・要確認75・共有のみ10
- テスト133件(従来117件+16件)。判定の一部を壊すミューテーション7パターンで、それぞれ対応するテストが失敗することを確認

### 既知の制約

- 総合判定の正解ラベルは作っていない。100件の成績は項目の充足(`audit_status`)で採点した従来の数字のままで、総合判定そのものの正答率は未評価
- 優先度の不一致(AI判定とPython判定の食い違い)も総合判定を要確認にする。AIの判断が正しくPython側のルールが粗い場合も要確認になる点に注意
- 履歴を使う監査(`/history/audit`)でも総合判定は同じ規則で作る。ただし、先に保存された記録は、あとから届く重複で更新されない(17章)

## 20. V0.8.1追補：評価で回答が欠けた件を不正解として数える(2026-10-04 追加)

### 背景

評価処理(`evaluate_predictions.py`)は、正解表とAIの回答の両方にあるrecord_idだけを採点していた。そのため、AIの回答が欠けた件があると、その件は分母にも分子にも入らず、正解率が実際より高く見えた(第三者確認の指摘)。同じrecord_idが回答に2回あると、後の行が黙って先の行を上書きする問題もあった。

### 設計

- 採点の対象は、正解表の全件。AIの回答がない件は、全項目を「不一致」として分母に入れる。正解が空欄の項目でも、回答なしは一致扱いにしない(空欄どうしの偶然の一致を防ぐ)
- `evaluation_summary.csv`の最後に`prediction_coverage`(正解表のうち回答があった件数と割合)を追加する。従来の指標の並び・意味は変えない
- `evaluation_details.csv`には、回答がない件の全項目を「(回答なし)」・不一致として出す
- コマンドは、回答がない件と、正解表にない回答の件数を表示する。正解表にない回答は採点しない
- `--allow-partial`を明示したときだけ、回答のある件に限って採点する(10件試験など)。このときも`prediction_coverage`が100%未満になるので、一部だけの採点であることが分かる。`run_trial_pipeline.py`にも同じ指定がある
- 正解表・回答のどちらかに同じrecord_idが複数ある場合は、エラーにする
- 正解表と回答に共通のrecord_idが1件もない場合は、これまでどおりエラー

### 確認

- 修正前の再現(実際のAI出力100件、`output/ai_predictions.csv`を同じ条件で監査した結果):全項目一致(正規化)は69/100。全項目一致でない31件のうち10件を回答から抜くと、69/90(76.7%)に上がった。修正後は、同じ操作で69/100のまま
- 100件すべてに回答がある場合は、従来の指標は全項目で同じ(差分0)。追加の`prediction_coverage`は100/100
- README「実API検証結果(100件)」の「うち残り90件」の数字は、先頭10件を外した一部の集計であり、この修正の影響を受けない
- テスト143件(従来133件+10件)。判定の一部を壊すミューテーション4パターンで、それぞれ対応するテストが失敗することを確認

### 既知の制約

- `--allow-partial`で採点すると、回答のある件だけの正解率になる。「全体の正解率」として扱わず、`prediction_coverage`とあわせて読むこと

## 21. V0.8.2追補：CSVをExcelで開くときの数式対策(2026-10-04 追加)

### 背景

`output/audit_result.csv`は、申し送りの原文(`message_text`)や、AIが取り出した作業内容などを含む。これらが`=`・`+`・`-`・`@`で始まると、CSVをExcelで直接開いたときに数式として実行される恐れがある(CSVインジェクション)。人が読む`audit_result.xlsx`は、文字のセルとして保存するため安全(18章)だが、CSVは対策がなかった。このCSVは評価処理(`evaluate_predictions.py`)が読み戻す採点の元データのため、中身は書き換えられない。

### 設計(3案から、作者が「別のCSVを出す」案を選んだ)

- `audit_result.csv`は、これまでどおり原文のまま出力する(評価処理が読み戻す)。READMEで「Excelで直接開かない」ことを明記する
- `audit_result_for_excel.csv`を追加する(`audit_rules.py`と`run_trial_pipeline.py`が、Excel版と同時に作る)。値が`=`・`+`・`-`・`@`・タブ・改行(CR)で始まる文字には、先頭に「`'`」を付ける。見出し行は変えない。Excelで開くと「`'`」が見えることがある
- `evaluation_details.csv`は、人が不一致を確認するための出力で、プログラムは読み戻さない。そのため、別ファイルを作らず、出力時に同じ無害化を行う
- `ai_predictions.csv`・`api_usage.csv`は、処理の途中で受け渡す元データであり、人が読む用途ではないため、原文のままにする

### 確認

- 修正前の再現:原文に`=1+1`、作業内容に`=HYPERLINK(...)`を入れて監査し、出力CSVをLibreOfficeでxlsxに変換すると、2つのセルが数式として扱われた。修正後は、Excelで開く用のCSVでは0件
- 実際のAI出力100件:`run_trial_pipeline.py`を通し、評価の数字は従来と同じ(項目の充足91/100、全項目一致(正規化)69/100、`prediction_coverage`100/100)。100件には危険な文字で始まる値がなく、2つのCSVの内容は同一(違うセル0)
- テスト150件(従来143件+7件)。無害化の取り消し・「@」の除外・安全CSVを出さない・採点用CSVまで無害化する・評価明細を無害化しない、の5パターンのミューテーションで、それぞれ対応するテストが失敗することを確認

### 既知の制約

- 先頭に「`'`」が付く値は、Excelでは「`'`」が見える(CSVにはExcelのような「文字として扱う」印がないための、一般的な方法)。人が読むには`audit_result.xlsx`が見やすい
- 数式の無効化は、セルの先頭の文字だけを対象にしている。途中に`=`がある文字は、Excelでも数式にならない
