# AI Handover Guard 仕様書 V0.3

## 1. 作品の位置づけ

- 大分類：AI Business Workflow Automation
- 作品名：AI Handover Guard
- 日本語名：AI引き継ぎ漏れ防止ツール
- 目的：申し送り文章から次の行動を抽出し、担当・期限・作業内容などの不足を警告する

## 2. 誰でも理解できる一文仕様

> 職場の申し送りを「誰が・何を・いつまでに」へ整理し、決まっていない項目を知らせるツール。

## 3. 利用者

| 利用者 | 必要な情報 |
|---|---|
| 一般職員 | 自分が担当する作業、期限、注意点 |
| 管理者 | 担当者不明、期限不明、期限超過、重要案件 |
| 改善担当者 | 漏れや曖昧さが多い連絡の傾向 |

## 4. V0.3の対象範囲

### 実装するもの

- AIへ渡す原文と、人間が決めた正解表の分離
- AI抽出後を想定したCSVの読み込み
- 必須項目の不足判定
- 警告理由の作成
- 監査結果CSVの出力
- 項目別正解率と全項目正解率の計算
- 単体テスト
- OpenAI APIを使った最大10件の安全な抽出試験
- 担当者名の敬称正規化
- 項目ごとの不一致明細
- 保存済みAI回答の監査・評価一括実行
- AI優先度とPython優先度の独立比較
- 優先度不一致の要確認表示
- 対応内容の完全一致と正規化一致の分離

### まだ実装しないもの

- メール、Slackなどへの自動通知
- GUI
- 実在する職場データの利用
- AIによる自動返信

## 5. 入力項目

| 項目 | 説明 | 必須 |
|---|---|---|
| record_id | 申し送りの識別番号 | 必須 |
| submitted_at | 登録日時 | 必須 |
| source_department | 発信部署 | 必須 |
| message_text | 元の申し送り文章 | 必須 |
| extracted_action | AIが抽出した作業 | 条件付き必須 |
| extracted_assignee | AIが抽出した担当者 | 条件付き必須 |
| extracted_deadline | AIが抽出した期限 | 条件付き必須 |
| extracted_priority | AIが判定した緊急度 | 必須 |
| action_required | 対応が必要か | 必須 |

## 6. 監査ルール

対応が必要な申し送りでは、次の3項目を必須とします。

1. 作業内容
2. 担当者
3. 期限

不足がある場合は `NEEDS_REVIEW`、不足がない場合は `READY` とします。対応不要の場合は `INFO_ONLY` とします。

優先度はAI結果を上書きせず、Pythonが原文から独立判定した `rule_priority` と並べます。不一致は `priority_audit_status=NEEDS_REVIEW` として人が確認できるようにします。

## 7. 視点をずらした部分

一般的なAI要約ツールは「文章を短くする」ことが中心です。本作品は、要約の上手さではなく「次の行動が実行可能な状態になっているか」を監査します。

## 8. 高値更新として示す部分

- AIと固定ルールを組み合わせる
- 正解ラベル付きデータで性能を測る
- 利用者別の表示を設計する
- 処理件数ではなく、不足項目の発見率を評価する
- 将来は通知まで含む一連の業務フローにする

## 9. 成功指標（将来版）

| 指標 | 意味 |
|---|---|
| 項目抽出正解率 | 担当・作業・期限を正しく取り出せた割合 |
| 不足検出再現率 | 本当に不足している案件を見逃さなかった割合 |
| 誤警告率 | 問題のない案件を誤って警告した割合 |
| 処理時間 | 人が確認する場合と比べた所要時間 |

## 10. 設計原則

- 処理単位ごとに見出しやコメントを付ける
- AIが不確かなときは、人による確認へ回す
- 業種固有ルールは設定で変更可能にする
- 元文章と判定理由を残し、後から確認可能にする
- 個人情報を含む実データは使用しない

## 11. V0.4追補：期限超過の判定(2026-09-29 追加)

### 背景

設計にあたり、次の考え方を前提とした。「顧客が『1週間以内に対応してください』と示していても、それは上限であって、4日目まで放置してよいという意味ではない」。また、即対応がどこまで求められるかは場面によって違う。仮の例として、社内向けの定例連絡では即対応が必ずしも求められない一方、通信販売の受注窓口で商品の破損・誤配送・品質不良といったクレームが発生した場合は、担当者がすぐ動くのが通例と考えられる。この2点から、「即対応の必要性は業種そのものより、案件の重さ(クレーム性)による」と整理した。

### 判定基準

- 緊急度「高」(既存のPython側緊急度自動判定を使用。クレーム・苦情・事故・安全等のキーワードで判定):文中の期限に関わらず、登録(`submitted_at`)から一定時間(既定4時間)以内に着手されていなければ`sla_audit_status=NEEDS_REVIEW`とする。この時間は`--sla-hours`で変更可能なサンプル値であり、実運用では業種・組織に合わせて調整が必要
- 緊急度「中」「低」:これまでどおり、文中の期限(`extracted_deadline`)を基準に判定する
- 対応不要(`action_required=false`)の案件は判定対象外(`NOT_APPLICABLE`)

### 既知の制約

現在のデータには、実際に「いつ着手したか」「いつ対応が完了したか」を示す項目がない。記録されているのは登録日時と文中の期限のみであり、この監査は「CSVに書かれた内容を見る一時点のスナップショット」である。実際の対応状況を継続的に追跡する仕組みには、今のところなっていない。判定の基準日時(`--as-of`)を指定できるのはこのためで、省略時は実行時刻を基準にする。

## 12. V0.4追補：重複候補の判定(2026-09-29 追加)

### 背景

同じ担当者・同じ作業内容の申し送りが短期間に複数回登録されている場合、誤って二重登録してしまったケースや、違う人が同じ案件を別々に報告したケースが考えられる。これらは対応漏れではなく対応の重複・混乱につながるため、V0.4のもう一つの判定として追加した(1つ目の候補案として提示した「同じ担当者・同じ作業内容が短期間に複数回登録されている」という定義を採用)。

### 判定基準

- 対象は`extracted_assignee`(担当者)と`extracted_action`(作業内容)が両方確定している案件のみ
- 作業内容は空白・句読点(全角/半角)の差を無視して比較する(表現のわずかな違いを別案件と誤認しないため)
- 同じ担当者・同じ作業内容の組み合わせが、一定時間(既定24時間、`--duplicate-window-hours`で変更可能なサンプル値)以内に複数回登録されていれば、両方(またはそれ以上)を`duplicate_audit_status=NEEDS_REVIEW`とし、どのIDと重複しているかをメッセージに残す
- 対応不要(`action_required=false`)の案件、担当者・作業内容が未確定の案件は判定対象外(`NOT_APPLICABLE`)
- 登録日時が読み取れない案件は`UNKNOWN`とする

### 既知の制約

- あくまで「目安」であり、重複＝誤りと決めつけるものではない。実際に別々の対応が必要な案件が、たまたま同じ担当者・同じ表現で短期間に登録されることもある
- 判定は今回読み込んだCSVの範囲内でのみ行われる。過去に監査済みのCSVとの突き合わせ(履歴をまたいだ重複検出)は、今のところ対応していない
- 100件の試験データ(`data/mock_ai_output.csv`)には、似た内容の案件が約2日おきに再発するパターンが含まれているが、既定の24時間の目安を超えているため重複候補としては検出されない。これは試験データの傾向によるものであり、実装の不備ではない(実際に短期間の重複を1件追加して、正しく検出されることを確認済み)

## 13. V0.4追補：実API検証件数上限の拡大(2026-10-01 追加)

### 背景

実API検証(`src/llm_extractor.py`)は、V0.2の時点から安全のため最大10件に固定していた。V0.4で元データ(`data/raw_handover.csv`)・正解表(`data/expected_labels.csv`)とも100件分がそろったことを受け、実API検証を100件へ広げることにした。あわせて、別のAPI(Claude)への切り替えも検討したが、既存の抽出プロンプトは2026年9月16日の10件検証でOpenAI(GPT-5.6 Luna)向けに確認済みのものであり、切り替えるとこの確認を最初からやり直す必要があるため、今回はOpenAIのまま上限のみを拡大する方針とした(Claude APIを試すのは、将来のFastAPI化のタイミングで別途検討する)。

### 変更内容

- `MAX_TRIAL_RECORDS`を10から100へ変更
- 既定の入力ファイルを`data/trial_10.csv`(10件固定)から`data/raw_handover.csv`(100件)へ変更。`trial_10.csv`の内容は`raw_handover.csv`の先頭10件と完全に一致するため、`--limit`を指定しない既定の動作(10件)は変わらない
- コマンドラインの`--limit`で1〜100件を指定できるようにした(既定値は10のまま)

### 既知の制約

- 100件での実行は2026-10-02に1回行い、結果は`docs/VALIDATION_REPORT.md`の8章に記録した(入力59,496トークン・出力7,594トークン、概算料金0.021012ドル)
- 100件は16種類の文型の繰り返しであり、100種類の独立した文章ではない

## 14. V0.4追補：100件検証で分かった既知の課題(2026-10-02 追加)

100件検証(`docs/VALIDATION_REPORT.md` 8章)で、次の課題が見つかった。いずれも修正はしておらず、既知の課題として記録する。結果を見てから同じ100件に合わせてプロンプトやルールを調整すると、点数は上がっても未知の文章への強さは示せないため、今回は記録を優先した。

### 14.1 曖昧な作業内容を要確認にできない

「例の件を○月○日17時までにお願いします」のように、作業内容が特定できない文が9件ある。正解は「作業内容が不明なので要確認(`NEEDS_REVIEW`)」だが、AIは作業内容に「例の件」「例の件をお願いします」と出力した。6章の監査ルールは作業内容が空欄かどうかだけを見るため、9件すべてが`READY`になった。

- 要確認にすべき49件のうち検出できたのは40件(不足検出再現率 約82%)
- 問題のない51件(`READY` 41件・`INFO_ONLY` 10件)を誤って警告したものは0件(誤警告率0%)

### 14.2 時刻のない期限の扱いが決まっていない

「○月○日までに」と時刻のない文が9件ある。正解表は期限を17:00としているが、これは文中にない前提である。プロンプトも時刻がない場合の扱いを指示しておらず、AIの出力は23:59(5件)・日付のみ(3件)・00:00(1件)にばらついた。

### 14.3 日付のみの期限が期限超過の判定をすり抜ける(既知の不具合)

11章の期限超過の判定は、期限を`YYYY-MM-DD HH:MM`の形式でしか読み取れない。14.2で日付のみが出力された3件は「期限が未確定のため判定できません」(`NOT_APPLICABLE`)と表示され、期限が書かれているにもかかわらず判定の対象から外れた。

## 15. V0.4追補：Excel版の出力(2026-10-02 追加)

### 背景

監査結果のCSVは項目名が英語で、列幅も調整できない(CSVには列幅を保存できない)。一般職員や管理者が読むには、日本語の見出しと読みやすい列幅が必要なため、人が読む用のExcel版を追加した。

### 設計

- `output/audit_result.csv`は変更しない。評価処理(`evaluate_predictions.py`)とテストが英語の項目名で読むため、機械が読む元データとして残す
- `output/audit_result.xlsx`を`src/excel_report.py`で追加する。`audit_rules.py`と`run_trial_pipeline.py`が実行時に同時に作る
- 1行目に英語の項目名、2行目に日本語見出し。値のうち判定系の5列(総合判定・緊急度の照合結果・期限超過の判定・重複の判定・対応要否)は「英語(日本語)」で併記する
- 列幅は内容の表示幅(全角2・半角1)から自動で決める。内容が長い列は2行に折り返して縮め、全行の高さをそろえる。3行以上が必要な行だけ高くする
- 見出し行と識別番号の列を固定し、日本語見出し行に絞り込みを付ける

### 既知の制約

- 見た目の確認は、作者が実際にExcelで開いて行った。他のExcel互換ソフトでは折り返しの位置が少し異なる場合がある
- 判定の日本語表記は、現在の判定名(`READY`など)に対する対応表である。判定名を増やした場合は`excel_report.py`の対応表も更新する
