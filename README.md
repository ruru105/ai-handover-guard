# やること抜けチェッカー(Action Item Checker)

旧称:AI Handover Guard(GitHubのリポジトリ名は`ai-handover-guard`のままです)。

> 申し送り文章から「誰が・何を・いつまでに」を整理し、対応漏れにつながる曖昧さを警告する業務フロー自動化ツールです。

## 何を解決する作品か

職場の申し送りには、次のような文章がよくあります。

> 部品の件、明日の午前中までに業者へ確認してください。

作業内容と期限は分かりますが、担当者が決まっていません。やること抜けチェッカーは、文章から必要な情報を構造化し、Pythonの固定ルールで不足項目を再確認します。

## 処理の流れ

1. CSVから申し送り文章を読み込む
2. AIが担当者・作業・期限・緊急度を抽出する
3. Pythonが必須項目の不足と優先度の食い違いを監査する
4. 警告付きの一覧をCSV／Excelへ出力する
5. 将来版では、重要案件だけを通知する

## この作品の特徴

- AIの要約結果をそのまま信用せず、Pythonのルールでも監査する
- 製造・介護・事務・物流など、業種を限定しない
- 一般職員には「自分がすること」、管理者には「担当・期限の未確定」を表示できる設計
- 正解ラベル付きデータでAIの抽出精度を評価できる
- 最終的には入力から記録・通知までをつなぐAI Business Workflow Automationを目指す

## 現在の段階

V0.3では、OpenAI APIの抽出結果をPythonが独立監査します。優先度はAI判定とルール判定を並べ、表現差は完全一致と正規化一致に分けて評価できます。

V0.4として、緊急度に応じた着手期限超過の判定を追加しました。緊急度「高」(クレーム・事故・安全に関わるものなど)は、文中の期限に関わらず、登録から一定時間(既定4時間、`--sla-hours`で変更可)以内に着手すべきという自社側の目安を基準にします。緊急度「中」「低」は、これまでどおり文中の期限を基準にします。これは「顧客が示す期限は上限であり、放置してよい猶予ではない」という考え方に基づく設計です。ただし現在のデータには実際に着手・完了した日時の記録がなく、この監査はCSVに書かれた内容を見る一時点のスナップショットです。判定の基準日時は`--as-of`で指定できます(省略時は実行時刻)。

さらにV0.4では、同じ担当者・同じ作業内容が短期間(既定24時間、`--duplicate-window-hours`で変更可)に複数回登録されていないかも確認します。誤って二重登録してしまった場合や、違う人が同じ案件を別々に報告した場合を見つける目安であり、必ずしも間違いと決めつけるものではありません。今回の100件の試験データでは重複候補は見つかりませんでした(データ内の似た案件は約2日おきの再発パターンで、24時間の目安を超えているため)。実際に3時間差の重複を1件加えて動作確認したところ、正しく両方が要確認になることを確認しています。

実API検証の上限は、2026年9月16日の10件検証時点では安全のため10件に固定していましたが、2026年10月1日に100件まで指定できるよう拡大しました(`data/raw_handover.csv`の全100件が対象。既定の`--limit`は変更しておらず、指定しない場合はこれまでと同じ10件です)。2026年10月2日に100件で実行し、結果を下の「実API検証結果(100件)」に記録しました。

```text
data/raw_handover.csv      ← AIに渡す問題
data/expected_labels.csv   ← 人間が決めた正解表
data/mock_ai_output.csv    ← 現段階の模擬AI回答
        ↓
src/audit_rules.py         ← 不足項目を監査
        ↓
output/audit_result.csv    ← 機械が読む結果(英語の項目名)
output/audit_result.xlsx   ← 人が読むExcel版(日本語見出し・列幅調整つき)
        ↓
src/evaluate_predictions.py ← 正解表と比較
        ↓
output/evaluation_summary.csv
output/evaluation_details.csv ← どの項目が違ったかを確認
```

## 実行方法

```bash
python src/audit_rules.py
python src/evaluate_predictions.py
```

`audit_rules.py`は、監査結果を`output/audit_result.csv`(評価処理が読む元データ)と、人が読むための`output/audit_result.xlsx`の両方へ出力します。Excel版は次のように作っています(`src/excel_report.py`)。

- 1行目に英語の項目名(小さい灰色)、2行目に日本語見出しを置く
- 総合判定・項目の充足などの値は「`NEEDS_REVIEW`(要確認)」のように英語と日本語を併記する
- 列幅は内容に合わせて自動で調整し、長い文は2行に折り返して列が横に伸びすぎないようにする
- 行の高さをそろえ、見出し行と識別番号の列を固定し、日本語見出し行に絞り込みボタンを付ける

Excel版はCSVから作り直せるため、GitHubには含めていません(`output/`は除外)。申し送りの原文など外部由来の文字列は、`=`で始まっていても数式にならないよう、必ず文字のセルとして保存します。

実際のAI回答を追加課金なしで監査・評価する場合：

```bash
python src/run_trial_pipeline.py
```

このコマンドは既存の `output/ai_predictions.csv` を使用し、新しいAPI通信は行いません。

## APIサーバー(V0.6)

他のツールやプログラムから、この作品の機能を使えるようにするためのAPIサーバー(FastAPI)です。次の3つの機能と、動作確認用の`/health`があります。

| 機能 | 入口 | 何をするか | 追加課金 |
|---|---|---|---|
| 監査 | `POST /audit` | AI抽出済みの申し送りを監査し、判定と件数のまとめを返す | なし |
| 期限超過の一覧 | `POST /overdue` | 監査したうえで、期限超過(要確認)の分だけを返す | なし |
| AIによる抽出 | `POST /extract` | 申し送りの原文から、やること・担当・期限をAIで取り出す | あり(有料API) |
| 履歴つきの監査 | `POST /history/audit` | 保存済みの履歴とも比べて監査し、今回の記録を保存する | なし |
| 履歴の件数 | `GET /history` | 保存している記録の件数 | なし |

起動方法(作品のフォルダで実行します)：

```bash
pip install -r requirements.txt
python -m uvicorn api:app --app-dir src
```

起動したら、ブラウザで `http://127.0.0.1:8000/docs` を開くと、画面から各機能を試せます。

`/audit`と`/overdue`の入力は、`output/ai_predictions.csv`の1行と同じ項目を持つ記録の一覧です。`as_of`(期限超過を判定する基準日時。例:`2026-09-20 09:00`。省略時は現在時刻)、`sla_hours`、`duplicate_window_hours`も指定できます。判定ルールはコマンドライン版(`audit_rules.py`)と同じ関数を使っており、実際のAI出力100件で、CSV版とAPI版の判定が全項目で一致することを確認しています。

`/extract`の安全設計(有料API通信のため、コマンドライン版より慎重にしています)：

- リクエストに`"confirm_paid_api": true`がなければ、通信せずに断る(コマンドライン版の`--execute`にあたります)
- 1回のリクエストは最大10件まで
- 自動再試行なし、1件当たりの最大出力300トークン(コマンドライン版と共通の処理)
- APIキーはサーバー側の`.env`だけで使い、リクエスト・レスポンス・エラーメッセージには出さない
- 結果にトークン数と概算料金(既定モデルのみ)を含める

テストでは、本物のAPIの代わりに偽のクライアントを使うため、課金は発生しません。

入力の決まり：`record_id`は空にできず、1回のリクエストの中で重複もできません(重複すると結果や履歴が混ざるため、`422`で断ります)。

認証機能は付けていません。自分のパソコン内(`127.0.0.1`)での利用に限り、インターネットに公開しないでください。

## 履歴の保存(V0.7)

これまでの重複候補の判定は、1回に渡した記録どうしの比較だけでした。V0.7では、申し送りの記録をSQLite(ファイル1つで動くデータベース)に保存し、**前回までに保存した記録とも比べて**重複候補を調べられるようにしました。

- 入口は`POST /history/audit`です。入力は`/audit`と同じで、`save`(既定はtrue)を指定できます。trueなら監査のあとで今回の記録を保存し、falseなら保存せずに比べるだけです
- 保存先は`output/history.db`です。GitHubには含めません(`output/*.db`は除外)
- 保存するのは、AI抽出済みの記録(監査ルールが読む9項目)だけです。判定結果は保存せず、基準日時によって変わるため毎回計算し直します
- 同じ`record_id`の記録は、新しい内容で置き換えます(自分自身とは比べません)
- 比べるのは、重複判定の時間枠(既定24時間)に入る履歴だけです。レスポンスの`history_compared`に、比べた履歴の件数が入ります
- 通常の`/audit`は、これまでどおり履歴を使わず、保存もしません

実際のAI出力100件を、時間がバラバラな4回に分けて監査したところ、履歴なしでは重複候補が4件、履歴ありでは9件になり、最終回の25件は100件まとめて監査した結果と全件一致しました。ただし、**先に保存された記録は、あとから重複が届いても「重複」には更新されません**(あとから届いた側に「先の記録と重複」と出ます)。まとめて監査した場合の13件には届きません。

## 総合判定と項目の充足(V0.8)

これまでの`audit_status`(「総合判定」と呼んでいました)は、実際には「作業内容・担当者・期限が書かれているか」だけを見ていたため、期限を過ぎていても重複の疑いがあっても「問題なし」と出ていました。V0.8で、2つを分けました。

| 項目 | 見るもの | 値 |
|---|---|---|
| `audit_status`(**項目の充足**) | 作業内容・担当者・期限がそろっているか(従来のまま) | `READY`(そろっている)/`NEEDS_REVIEW`(不足あり)/`INFO_ONLY`(共有のみ) |
| `overall_status`(**総合判定**。新規) | 上に加えて、期限超過・重複候補・優先度の不一致・判定不能がないか。1つでもあれば要確認 | `READY`(問題なし)/`NEEDS_REVIEW`(要確認)/`INFO_ONLY`(共有のみ) |

`overall_message`に、要確認の理由(例：「要確認：期限超過・重複候補」)が入ります。Excel版では、日本語見出しは「項目の充足」「総合判定」です。

あわせて、次の扱いを変えました。

- 登録日時が読めない、または期限が書かれているのに書式が読めない(「来週中」「2026/09/18」など)場合は、「判定対象外」ではなく「判定不能」(`UNKNOWN`)とし、総合判定を要確認にします。期限が空欄の場合は、従来どおり「判定対象外」です
- `action_required`が`true`/`1`/`yes`/`y`または`false`/`0`/`no`/`n`(大文字小文字・前後の空白は問いません)のどちらにも読めない場合(`tru`や空欄など)は、黙って「対応不要」にせず、項目の充足・総合判定とも要確認にします。APIでは、このような値はエラー(422)で受け付けません
- APIの`summary`に`overall_ready`と`overall_needs_review`を追加しました(従来の`ready`・`needs_review`・`info_only`は、項目の充足の件数です)

実際のAI出力100件(基準日時 2026-09-20 09:00)での件数は次のとおりです。従来の項目は、修正前後で1件も変わっていません。

| | 問題なし | 要確認 | 共有のみ |
|---|---:|---:|---:|
| 項目の充足(従来の「総合判定」) | 50 | 40 | 10 |
| 総合判定(新) | 15 | 75 | 10 |

総合判定の要確認が増えるのは、期限超過54件・重複候補13件などが、これまで「問題なし」に紛れていたためです。上の「実API検証結果(100件)」の「監査判定」(91/100)は、従来どおり項目の充足(`audit_status`)で採点した数字で、変わりません。

## 実API検証結果(100件)

2026年10月2日に、架空の申し送り100件を同じ条件(GPT-5.6 Luna、V0.3のプロンプトのまま)で1回だけ抽出しました。結果を見てからの調整や、やり直しは行っていません。

| 評価項目 | 100件 | うち先頭10件 | うち残り90件 |
|---|---:|---:|---:|
| 対応内容・完全一致 | 59/100 | 7/10 | 52/90 |
| 対応内容・正規化一致 | 70/100 | 8/10 | 62/90 |
| 担当者 | 100/100 | 10/10 | 90/90 |
| 期限 | 91/100 | 10/10 | 81/90 |
| AI優先度 | 97/100 | 10/10 | 87/90 |
| Python優先度 | 100/100 | 10/10 | 90/90 |
| 対応要否 | 100/100 | 10/10 | 90/90 |
| 監査判定 | 91/100 | 10/10 | 81/90 |

100件は100種類の文章ではなく、16種類の文型を番号や日付を変えて繰り返したものです。10件検証で試していなかった文型で、次の課題が見つかりました。修正はしておらず、既知の課題として記録しています。

- 見逃し9件：「例の件を○月○日17時までにお願いします」のように作業内容が曖昧な文で、AIが作業内容に「例の件」と書き入れたため、空欄かどうかだけを見るPython監査が「問題なし」と判定しました。要確認にすべき49件のうち検出できたのは40件(約82%)です。問題のない51件を誤って警告したものは0件でした。
- 期限の不一致9件：「○月○日までに」と時刻のない文です。正解表は17時としていますが、これは文中にない前提です。AIの出力も23:59・日付のみ・00:00の3通りにばらつきました。
- 上記のうち日付のみで出力された3件は、期限超過の判定が読み取れず「期限が未確定」と表示されていましたが、2026年10月2日に修正しました(日付のみの期限は、その日の終わりまで有効として判定します。詳しくは [`docs/SPEC.md`](docs/SPEC.md) の14.3)。
- AI優先度の不一致3件は、Pythonの独立判定との食い違いとしてすべて要確認になりました。

入力59,496トークン・出力7,594トークン、概算料金は0.021012ドルでした。内訳は [`docs/VALIDATION_REPORT.md`](docs/VALIDATION_REPORT.md) の8章に記録しています。

## 評価指標の読み方

- `action_exact`：正解表との文字列完全一致
- `action_normalized`：空白・句読点・末尾の「する」をそろえた一致
- `priority_ai`：AIが出した優先度の一致
- `priority_rule`：Pythonが原文から独立判定した優先度の一致
- `all_fields_exact`：主要項目がすべて完全一致した割合
- `all_fields_normalized`：対応内容を正規化した上で主要項目がすべて一致した割合
- `prediction_coverage`：正解表のうち、AIの回答があった件数

**回答がない件は不正解として数えます。** 正解表のすべてのrecord_idが採点の対象で、AIの回答が欠けた件は、全項目「不一致」として分母に入れます(回答が欠けた件だけを外すと、正解率が実際より高く見えるためです)。`prediction_coverage`が100%未満のときは、評価の実行時に「回答がない正解表のID」の件数が表示され、`evaluation_details.csv`には「(回答なし)」の行が残ります。10件試験のように、一部だけを試したときに回答のある件だけを採点したい場合は、`python src/evaluate_predictions.py --allow-partial`(または`python src/run_trial_pipeline.py --allow-partial`)と明示します。同じrecord_idが複数ある場合は、どちらを採点したか分からなくなるため、エラーにします。

## API接続の安全設計

- 既定は10件、`--limit`で最大100件まで指定可能(2026-10-01に上限を拡大。指定しない場合は従来どおり10件)
- 既定モデルはGPT-5.6 Luna
- `--execute` を明示しない限りAPI通信しない
- 自動再試行なし
- 1件当たりの最大出力を300トークンに制限

- APIキーは `.env` に保存し、GitHubには公開しない

安全確認のみを行う場合：

```bash
python src/llm_extractor.py
```

有料API通信は、APIキーと利用上限を確認した後だけ実行します。

```bash
python src/llm_extractor.py --execute --limit 10
```

## 注意事項

サンプルデータはすべて架空です。個人情報や実在する職場の内部情報は使用しません。

- 実API検証は架空データ100件(16種類の文型)を1回実行したのみであり、本番運用の精度保証ではありません。
- 作業内容が曖昧な文(「例の件」など)は、現在の監査では要確認にできません。
- 優先度ルールはサンプル用です。実運用では業種や組織に合わせた設定が必要です。
- AIの出力は実行ごとに表現が変わる可能性があります。
- `.env`、APIキー、実在する個人情報をGitHubへ登録しないでください。
